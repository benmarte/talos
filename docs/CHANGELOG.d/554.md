- lean: fewer GitHub API calls per issue (#554, part of #558). A stubbed issue
  lifecycle (`tests/test-api-calls.sh`) went from 49 GraphQL and 86 REST calls to
  6 GraphQL (-88%) and 68 REST (-21%).
  - **CI wait backs off.** `pr-checks-required --wait` polls at 30 s, then 60 s,
    then 120 s (it was a fixed 30 s), each step clipped to the time left; the
    deadline and exit codes are unchanged. The commit-status read stays skipped
    when check runs already cover every required check.
  - **One set of reads per approval.** `post-approval` makes a per-pass cache
    directory (`TALOS_PASS_CACHE`) that `pr-head`, `read-comments`, `comment-pr`,
    `label-pr`'s marker guard and the `check-approval-sha` self-check share: the
    PR, its comments and the login are read once before the writes and once
    after. Any write through the GitHub client empties the cache (the login
    aside), comments are bound to the head SHA of the cached PR, only successful
    reads are stored, and a process outside the owning pass ignores the
    directory. A standalone verb has no pass and reads as before. One approval is
    7 REST calls, not 10; head-SHA binding and the stale re-stamp are unchanged.
  - **Board moves cost 4 GraphQL calls for the first, 1 for each later one**
    (the `github` provider; it was 5-6 per move). The item is found by issue (one
    `projectItems` query) instead of paging `item-list --limit 400`; the owner and
    repo come from config (`board.owner`, `vcs.repo`) before `gh repo view`; and
    the project id, the status field's option ids and each issue's item id are
    cached per run in the existing `board-validated-*` file (owner and project
    number are also checked inside it, 6 h TTL). A stale cache costs one retry
    with fresh ids, not a lost move. The `github-api` provider's board path is
    unchanged (it still pages `items(first:100)`).
  - **Notifications stop asking GraphQL.** `scripts/pipeline-meta.sh` supplies
    the board name and repo URL (from `vcs.repo` or the checkout's remote, no
    call) and issue/PR titles (one REST read, kept 6 h in a user-private file);
    `pipeline-notify.sh` used to run `gh repo view` twice, `gh issue view` and
    `gh pr view` on every message. With nothing to derive from it falls back to
    `gh repo view`.
  - **`talos.sh run` reads the collected state once per state.** The in-flight
    list read and the first `next` share one collect (`TALOS_COLLECT_CACHE`, a file
    in the run's private dir); every writing verb (`done`, `gate`, `docs-gate`,
    `post-merge`, `sweep`, `claim`, and a claim inside `next`) empties it, a copy
    older than two minutes is not used, and a failed or non-JSON read is never
    kept. A standalone `next` or `state` is unchanged.
