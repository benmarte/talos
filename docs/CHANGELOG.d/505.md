- **`pipeline-status-file.sh refresh` no longer exits 1 when a concurrent refresh in the same checkout wins the ref lock (#505).** Two refreshes in one checkout could make a `git fetch origin <base>` fail with `error: cannot lock ref 'refs/remotes/origin/<base>': is at X but expected Y` (the other process's fetch or push had just moved the tracking ref), and the loser exited 1 with only `git fetch origin <base> failed`, before it reached the push-race handling. The fetch is now retried up to 5 times (0.2 s apart), and the final give-up message carries git's own error. The parallel smoke test in `tests/test-status-file-refresh.sh` prints `par1.out` and `par2.out` when a process fails, and two new cases drive a git shim that loses the ref lock once or forever.
