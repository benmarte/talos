# Changelog

One line per change, newest first. Releases before 0.17.0 are listed in the last line.

## [Unreleased]
- fix: a claude stage no longer waits about 115 s on each refused tool call under a terminal wrapper (cmux) that adds a `PermissionRequest` hook: `pipeline-agent.sh` starts `claude` with `CMUX_CLAUDE_HOOKS_DISABLED=1` unless the caller set it, and the QA profile says a refused command is not a block and the verdict must still be posted.
- feat: a stage can no longer change the resolved pipeline config: every claude role is denied Edit/Write on it, and `pipeline-agent.sh` checksums the user, project and repo config files around any runner and exits 78 (`stop reason=config-mutated role=<role> file=<path>` under `talos.sh run`) when one changed; the new `docs.paths` key (default `README.md`, `docs/*`, `scripts/pipeline-defaults.sh`) names where `docs-gate` looks for docs, including under `.claude/`, where the docs role needs `claude_permission_mode: auto` (a startup warning says so)
- feat: `pipeline-criteria.sh red-check <N> [<ref>]` checks each criterion's kind against the red commit in a throwaway worktree (`kind-mismatch`, `id-collision`), and `talos.sh run` calls it once after the first-round developer opens the PR: a `(test)`/`(same)` mismatch is re-posted as a revised `**PM spec:**` and the run continues, an id collision stops `spec-unusable detail=id-collision` before reviewer
- fix(azure): `pr-files` lists a deleted file from the change's `originalPath` (ADO sends `item.path` null) and a rename under both names, so `check-pr-files` no longer fails closed on a PR that deletes a file; an entry with neither path is still a parse failure
- fix: `talos.sh run` exports one `PIPELINE_RUN_ID` per run (kept across the exec after a merge, a caller's own value wins), so the Azure board column lookup and its `board-states-collide` warning happen once per run instead of on every status move
- fix(azure): the board column lookup uses the project's default team when `board.azure_team` is unset (the backlogs API answers 404 without a team), warns `board-team-unmatched` when `vcs.azure.area_path` matches no team, and `board-columns-unavailable` names the failed `step` (teams, backlogs or columns)
- test(routing): `tests/test-routing-e2e-github.sh`, `-azure.sh` and `-gitlab.sh` drive `talos.sh next --issue` from `pipeline:ready` to the merge action over each provider's real `pipeline-vcs.sh` adapter and stubbed CLI, so a missing adapter verb or JSON key fails a routing step
- feat(gitlab): `pr-checks-required` judges the MR's head pipeline (empty `merge.required_checks`) or its named jobs instead of always exiting 1, with github's exit codes and summary lines, so the merge gate can pass on gitlab; no head pipeline, or one for another commit, is pending
- feat(gitlab): `pr-head`, `read-comments`, `read-attempt`, `record-attempt`, `check-attempt`, `check-approval-sha` and `post-approval` run on gitlab, and `has-spec` accepts it, with the azure output, exit codes and marker formats (MR and issue notes through `glab api`), so the code driver no longer gets `unknown verb`
- feat(gitlab): `list-issues`, `list-prs` and `view-issue` print the GitHub-shaped JSON the router reads (`number`, `labels[{name}]`, `headRefName`, `baseRefName`, `isDraft`, `isCrossRepository`, raw `glab` keys kept), and `view-issue` adds the issue's notes and honours `--spec` and `--since-stage`
- feat(azure): a board move takes the work-item State from the team board's column named like the status (`board.azure_team`, `board.azure_board`, `board.azure_columns.<status>`; an explicit `board.azure_states.<status>` still wins), warns `board-states-collide`, `board-column-unresolved` and `board-columns-unavailable`, and reports the `System.BoardColumn` read back after the update.
- fix(tests): the verify shards are balanced on real durations again: `tests/timings.txt` is refreshed for every test file and `test-talos-run.sh` (about 400 s alone) is split into four files, so no shard passes the 600 s cap; `tests/test-shard-weights.sh` fails a test file with no timing entry and a shard heavier than its bound
- fix(qa): a `(test)` criterion that is green at the red commit and at the head is a regression guard (`AC<n> guard green@head (green at red@<sha8>)`) when another criterion went red then green and no other FAIL line exists, so a mixed spec no longer ends `spec-unusable`; all criteria vacuous still does

## [0.19.0] - 2026-10-16
- docs: `post-approval`, `check-approval-sha` and `has-spec` are documented as running on Azure too (the stage profiles no longer call `post-approval` GitHub-only); the reference documents the `comment-issue` / `comment-pr` body rules and the `map` verb, `qa.md` lists the `flaky` and `e2e` `qa-run` lines, `talos.pipeline.json.example` keeps the `*.example` approval waiver, and a guard test catches a GitHub-only claim about an Azure verb
- feat(qa): `qa-run` re-runs a failing head run once and names a test that passed the second time `AC<n> FAIL flaky`, which stops the run for the owner (`stop reason=qa-flaky`) instead of starting a fix round; a repo-only `verify.e2e` command runs once on a green draft, and a non-zero exit is a QA FAIL with its output tail
- feat(verify): a repo-only `verify.targeted_commands` list of `{match, run, pass, fail}` entries tells `qa-run` and the developer how to run one test file of another stack (dotnet, vitest, ...) and how to read its pass/fail lines, so red/green is proved without a hand-run override; `pipeline-criteria.sh map` takes `--pass-re` / `--fail-re`
- feat(qa): `qa-run` also runs the red commit's version of each `Tests:` file the PR changed since, against the head code (the frozen run), and prints `frozen@head` or `AC<n> FAIL weakened (red-commit test fails at head)`, so a fix round cannot weaken a test after the red proof; `--ack-changed <reason>` records a change made on purpose as `weakened-ack`
- fix(ci): the test workflow and the shipped `templates/ci/github-tests.yml` no longer install PyYAML on macOS; Talos config is JSON only and every remaining `yaml` import is optional, so the step only failed when the runner image changed
- feat(criteria): a `(same: <why>)` criterion kind for behaviour that must not change; `qa-run` passes it when its tests are green at the red commit and at the head (`AC<n> PASS same red@<sha8> green@head`) instead of failing it as `vacuous`.
- fix(vcs): `comment-issue` and `comment-pr` refuse a positional or `--body` body that is one whitespace-free token naming a readable file, relative (`.talos/x.body`) or absolute, with the "use `--body-file`" message; a `--body-file` or stdin body is never read as a path, and a token that is not a file is still posted as text
- fix(gate): the same-area check of `gate fix-round` counts two findings comments of one unchanged PR head as one round, so a re-review after a restart no longer asks the owner a design question; the reviewer, security and adversarial profiles end a findings comment with `<!-- talos:reviewed sha=<head> -->` (new `talos:reviewed` marker), and a comment without it keeps counting as its own round
- feat(azure): `upsert-pr-comment`, `mark-needs-owner` and `list-needs-owner` work on Azure DevOps PRs, so the `talos:spend` comment is kept in one thread comment and an owner question is posted and read back on the PR; `create-pr` and `merge-pr` pass `--squash` from `merge.method` (squash by default, with the PR title as the squash message), so a squash-only branch policy reads as met
- fix(run): a PR left blocked by a reviewer's `**Blocked** — ` findings comment (the `blocked.md` shape) is taken to the developer fix round by a later `talos.sh run --issue`, not answered `wait reason=blocked`; the resume reads review findings through one shared pattern (`_TALOS_FINDING_RE`) that also keeps the `**Review:** CHANGES` and `**Security:** FINDINGS` shapes
- fix(run): a reviewer, security or adversarial stage whose final message has no verdict word but whose approval is stamped on the PR (its label present and `check-approval-sha --stale-list` not naming it) is read as `APPROVED` / `CLEAR` instead of stopping `verdict-unreadable`; a verdict word still wins, and only approval is read from the stamp
- fix(agents): the developer and docs profiles write their body to a literal `.talos/<role>-<name>.body` file, and the roles without a Write tool (validator, reviewer, security, qa, adversarial) post from stdin with `--body-file -`, so no `*.md` body file is written and a project's "no stray .md/.txt" `PreToolUse` hook can no longer stop a stage from posting
- fix(azure): `vcs.repo` `project/name` is reduced to the repository name (its last path segment) in every git REST URL and `--repository` argument, so `view-pr`, `create-pr`, `find-pr` and the PR label and comment writes no longer 404; `label-pr` and `comment-pr` exit non-zero when the write fails or the org/project/repo cannot be resolved
- fix(azure): work-item descriptions and comments keep a single newline as `<br>` (pandoc `hard_line_breaks`, python-markdown `nl2br`, the built-in fallback) and read back as a newline, so a spec's `**Tests:**` line no longer swallows the next line; work-item comments are listed oldest first, so a revised `**PM spec:**` takes effect
- fix(azure): `view-pr` and `check-approval-sha` read the PR's labels from the PR labels API (`az repos pr show` always answers `labels: null`), a failed labels read fails closed, and the driver's label reader treats `labels: null` as no labels

- fix(azure): `view-issue` (and `--spec` / `--since-stage`) includes the work item's comments with each stored-HTML body converted back to markdown, so a PM spec posted through `comment-issue` is readable by `pipeline-criteria.sh` (`spec-usable`, `qa-run`)
