- **Optional adversarial pre-merge stage on a per-role backend (#237, split from #167 S1).** New optional role `adversarial` (`roles.adversarial`, default `false`) attacks the diff for vacuous tests, weak regex/allow-list patterns, secret shapes, and unverified PR-body claims -- an independent second opinion, typically paired with `agents.roles.adversarial.runner: custom` + a local `runner_cmd` (e.g. a llama.cpp `llama-server` endpoint) so it is cheap enough to run on every PR. `scripts/pipeline-contract.sh` gains `adversarial` in `TALOS_ROLES` and `TALOS_APPROVAL_ROLES`, with `adversarial:approved` added to `TALOS_APPROVAL_LABELS` (index-aligned, after `security`) -- `post-approval <pr> adversarial` and `check-approval-sha` work automatically since both derive their valid-role/label sets from the contract; `check-approval-sha` only ever validates a label that is present on the PR, so an absent `adversarial:approved` (the default, disabled state) is simply never checked. `roles.adversarial` is added to `pipeline-config.sh`'s known-key list. New profile `agents/adversarial.md` follows the same skills-sentence convention as every other profile (names `agent-skills:doubt-driven-development`, `agent-skills:security-and-hardening`, `agent-skills:code-review-and-quality`, `superpowers:verification-before-completion`, `verifying-agent-gate-verdicts`, `testing-llm-gated-pipelines`) and embeds its full method inline as six numbered steps (read diff, hunt vacuous tests via a revert-in-mind check, stress every pattern with 3 matching/3 non-matching inputs, scan for secret shapes, verify every PR-body claim, verdict) so it works even on harnesses with no skill mechanism -- only a bare `runner_cmd` to a model endpoint lacks one. `skills/pipeline/SKILL.md` dispatches it as a new Step 3e Phase 3, after security's phase 2 completes, gated on `roles.adversarial` and using the existing #167 per-role runner rule; Step 4's merge-readiness list gains a fifth bullet (`adversarial:approved` present, if `roles.adversarial = true`) and its stale-role re-dispatch list gains an `adversarial` branch. Zero behaviour change when the role is absent or `false`: no dispatch, no approval requirement, no stale-role handling. Documented in the README roles table/config row and a new "Second opinion on a local model" section in `docs/user-guide.md` with the llama.cpp worked example; both example configs carry the new `roles.adversarial`/`agents.roles.adversarial` keys (commented in the YAML example, described in the JSON example's `_note`, since JSON has no comment syntax). No version bump.

- **Local `.talos/events.jsonl` audit log, plus `scripts/pipeline-events.sh` reader (#183).** Outcomes previously left a durable trace only via `hooks.post_stage` (#182), which requires an external sink to be configured. Now every `post_stage` payload -- the same JSON schema `hooks.post_stage` receives on stdin -- is also appended, as one line, to a local audit log, independently of whether `hooks.post_stage` itself is configured; disabled projects (or ones without a hook wired up) still get a free, local, machine-readable run history for post-mortems and crash resumption. New config keys `events.enabled` (default `true`) and `events.path` (default `.talos/events.jsonl`), added to `pipeline-config.sh`'s known-key list and documented with a commented example in both example configs. The path resolves relative to the **main repository root** via `git rev-parse --git-common-dir` (not the current worktree's own `.git` dir), so every linked worktree of a repo shares the one log file -- a developer/QA/reviewer stage running from inside a per-issue worktree still appends to the main checkout's log, never a worktree-local copy; an already-absolute `events.path` is used as-is. Appends are a single `printf '%s\n' >>` -- one `O_APPEND` write syscall, atomic on POSIX for the well-under-`PIPE_BUF` line lengths a JSON event produces, so concurrent stages (`issues.max_parallel` > 1) interleave whole lines, never partial ones; no lock file is used. A write failure (unresolvable path, permissions, disk full) is a stderr note only and never affects `pipeline-hooks.sh`'s exit code. `.talos/` was already gitignored. New `scripts/pipeline-events.sh` (added to `install.sh`'s script copy list) provides `path` (prints the resolved log path), `list [--issue N] [--role R] [--event E] [--last K] [--json]` (default: a compact one-line-per-event table -- ts, event, role, issue, pr, verdict, summary truncated to 80 chars; `--json` prints one JSON object per line), and `tail [--issue N]` (shorthand for `list --last 20`); parsing is done with python3, and a malformed line is skipped with the count reported once on stderr, never fatal. `tests/test-events-log.sh` covers: `post_stage` appends one valid JSON line whether or not `hooks.post_stage` is configured (never two lines when it is); `events.enabled: false` produces no file; the path resolves to the main repo from inside a linked worktree (a scratch repo plus `git worktree add` under `mktemp`); reader filters (`--issue`/`--role`/`--last`) and `--json`; a malformed line is skipped with the reported count; and 8 concurrent `post_stage` calls produce 8 intact, non-interleaved lines. No version bump.
- **`hooks.post_stage`: run a command after every verdict, approval, block, and merge, with a JSON outcome event on stdin (#182).** Outcomes previously left Talos only as GitHub comments and chat notifications -- there was no machine-readable event an external tool (metrics, cost tracking, a project memory) could subscribe to. New config key `hooks.post_stage` (default `""` -- disabled), sharing `hooks.timeout_s` with `hooks.pre_dispatch`. `scripts/pipeline-hooks.sh` gains `post_stage <event> <role> <issue> [--pr N] [--sha S] [--verdict V] [--summary "..."] [--details-file F] [--attempt stage:count:total] [--duration-s N]`, sharing its watchdog/timeout machinery and repo-resolution helper with `pre_dispatch` (both refactored into `_hooks_run`/`_hooks_timeout_s`/`_hooks_repo` -- no copy-paste between the two verbs). Stdin JSON: `{event, role, issue, pr, repo, sha, verdict, summary, details, attempt:{stage,count,total}|null, model, runner, duration_s|null, ts}`, built with python3 `json.dumps`; fields the caller didn't supply (`pr`, `sha`, `verdict`, `model`, `runner`) are `null` rather than omitted, matching `pre_dispatch`'s existing convention. `model` reads `agents.roles.<role>.model` falling back to `agents.model`; `runner` reads `agents.runner`. `duration_s` is `null` unless the caller passes `--duration-s` -- no stage-timing infrastructure was added in this change (scope note from PM review: threading timers through every stage was explicitly out of scope). Same never-block contract as `pre_dispatch`: a non-zero exit or a timeout is a silent no-op with exactly one stderr line; the helper is itself foreground and always returns (never leaves an orphaned watchdog) before this script exits. Wired into the adapter path: `scripts/pipeline-agent.sh` no longer `exec`s straight into the runner (`claude`/`codex`/`gemini`/`antigravity`/`pi`/`custom`) -- each branch now runs the runner as a normal foreground command, captures its exit code, and fires exactly one `post_stage stage_complete <role> <issue> --verdict PASS|FAIL` call (verdict from the exit code) before exiting with that same code, so `pipeline-agent.sh`'s own exit status is unchanged for every caller. `TALOS_STAGE_DURATION_S`, if the caller sets it, is forwarded as `--duration-s`. On the native orchestrator path, `skills/pipeline/SKILL.md`'s Conversation stream protocol gains Rule 3 (after Rule 1 findings-comment and Rule 2 orchestrator-relay): fire `hooks.post_stage` after every role relay and every lifecycle event (pr-opened, merged, blocked, issue-closed), with a two-line example; Step 4's post-merge list gets a one-line reminder to fire it for `merged`/`issue-closed`. `hooks.post_stage` is added to `pipeline-config.sh`'s known-key list and documented with a commented example in both example configs, next to `hooks.pre_dispatch`. `tests/test-hooks-post-stage.sh` covers exact payload fields for a verdict event (qa/PASS) and a lifecycle event (merged, verdict/attempt/duration_s all null), disabled-by-default, a failing/slow hook (exit 0, one stderr note, no orphaned watchdog), and the adapter path emitting exactly one `stage_complete` event per run with the verdict flipping PASS/FAIL on the stub runner's exit code; `tests/test-skill-names.sh` asserts Rule 3's text is present in `SKILL.md`. No version bump.
- **`notifications.cmd`: a generic command sink for pipeline events (#184).** `scripts/pipeline-notify.sh` only shipped Slack, Discord, Teams, and Buzz sinks -- anything else (a local desktop notifier, a webhook relay, a log shipper) needed a code change. New config keys `notifications.cmd` (default `""` -- disabled) and `notifications.cmd_timeout_s` (default `10`, validated as a positive integer through the same `_validate_int_key` pattern `verify.timeout_ms`/`hooks.timeout_s` already use, on both `pipeline-config.sh`'s `--dump` path and its single-key path) are read via the `cfg()` cache. When `notifications.cmd` is set, it runs (via `sh -c`) after the four existing sinks, for every event that passes the existing `notifications.events` filter -- the same event-filter check the other sinks already go through, no changes needed. The command receives a JSON payload on stdin (`event, ref, message, thread_key, fields, repo, issue`, built with python3 `json.dumps`, never string-concatenated): `message` is the same rendered text the other sinks build their message from, and `fields` reuses the same platform-neutral metadata array (`{label,text,url}`) the other sinks already render natively. Bounded by a portable timeout mirroring `pipeline-hooks.sh`'s `hooks.pre_dispatch` watchdog (#219/#181) -- its own process group (`set -m`) plus a background watchdog subshell sending SIGTERM then SIGKILL once `notifications.cmd_timeout_s` elapses -- reimplemented inline in `pipeline-notify.sh` rather than sourced, since that watchdog logic lives inline inside `pipeline-hooks.sh`'s `pre_dispatch()` interleaved with hook-specific JSON building and isn't exposed as a standalone sourceable function. A missing command, a non-zero exit, or a timeout logs exactly one line to stderr and is otherwise a no-op; `pipeline-notify.sh` still exits 0 and the cmd sink never blocks the sinks before it. `notifications.cmd`/`notifications.cmd_timeout_s` are added to `pipeline-config.sh`'s known-key list (#176 guard) and documented with a commented example in both example configs. `tests/test-notify-cmd.sh` covers disabled-by-default, the exact payload shape (asserted via python3), event filtering, a failing command, a slow command exceeding the timeout, no orphaned process surviving a timeout, and the cmd sink running alongside a stub Slack webhook sink in the same invocation. No version bump.

- **`hooks.pre_dispatch`: run a command before each stage and prepend its output to the prompt (#181).** Talos had no way for an external tool (a project memory store, a cost budget, a repo-specific style guide) to add context to a stage's prompt. New config keys `hooks.pre_dispatch` (default `""` -- disabled) and `hooks.timeout_s` (default `30`, validated as a positive integer through the same `_validate_int_key` pattern `verify.timeout_ms`/`verify.ci_wait_s` already use, both on `pipeline-config.sh`'s `--dump` path and its single-key path) are read via the `cfg()` cache. New `scripts/pipeline-hooks.sh` implements `pre_dispatch <role> <issue> [<pr>] [<worktree_path>] [files_hint...]`: builds the documented stdin JSON (`role, issue, pr, repo, base_branch, worktree_path, files_hint[]`) with python3 `json.dumps` (never string-concatenated), exports `TALOS_ROLE`/`TALOS_ISSUE_NUMBER`/`TALOS_WORKTREE_PATH`, and runs the configured command via `sh -c` under a portable timeout -- its own process group (`set -m`) plus a background watchdog subshell that sends SIGTERM then SIGKILL once `hooks.timeout_s` elapses, since macOS ships no `timeout(1)` by default. A non-zero exit, a timeout, or empty stdout is a silent no-op -- nothing is printed, the prompt is left byte-identical to the no-hook case -- with exactly one line on stderr; the helper always exits 0 and never blocks dispatch. Non-empty stdout is prepended to the prompt as `## Context\n<output>\n---`. Wired into the adapter path (`scripts/pipeline-agent.sh`, right after the prompt is assembled) and the native orchestrator path (`skills/pipeline/SKILL.md`'s Harness compatibility section, applying to every "spawn a subagent" step, with a one-line reminder on the developer and QA blocks). `hooks.pre_dispatch`/`hooks.timeout_s` are added to `pipeline-config.sh`'s known-key list (#176 guard) and documented with a commented `hooks:` block in both example configs. `tests/test-hooks-pre-dispatch.sh` covers the adapter path end to end: hook output landing at the top of the prompt the stub `runner_cmd` receives, failing/slow(timeout)/empty hooks each producing a prompt byte-identical to the no-hook case, the stdin JSON schema (asserted via python3), and disabled-by-default. No version bump.

- **`tests/run-tests.sh --for <path>` / `--changed [<base-ref>]`: convention-based targeted test discovery (#197).** `agents/developer.md`, the README config table, and `docs/user-guide.md` already promised `tests/run-tests.sh --for <changed files>` for `verify.targeted: true`, but the flag did not exist -- developers always ran the full suite while iterating. `--for <path>` (repeatable) and `--changed [<base-ref>]` (derives paths from `git diff --name-only <base-ref>...HEAD` plus uncommitted and untracked changes, default base ref `origin/main`) now select test files by convention instead: `scripts/pipeline-<name>.sh` -> `tests/test-<name>*.sh`; `tests/test-*.sh` -> itself; `agents/*.md`/`skills/**`/`templates/**` -> `tests/test-skill-names.sh` plus any test file whose contents reference that path's directory (found via `grep -l`); `scripts/pipeline-vcs.sh` additionally always selects `test-verb-parity.sh`, and `scripts/pipeline-config.sh`/`scripts/pipeline-cfg-cache.sh` additionally always select `tests/test-config*.sh`. `tests/stubs/*`, `tests/helpers.sh`, `tests/run-tests.sh` itself, `talos.pipeline.*`, `.github/**`, and any path matching no rule fall back to the full suite (fail-safe; the unmapped case also prints a one-line stderr note). The selected file list is printed before running, and both flags compose unchanged with `--quiet`, `-j`/`TALOS_TEST_JOBS`, `--no-cache`, and `--repeat`. **Robustness fix found while testing this:** a selection that legitimately matches zero test files (a realistic outcome of `--for`, not just a mistyped pattern) previously crashed with a raw `ALL_FILES[@]: unbound variable` under bash 3.2/macOS's `set -u` instead of printing `RESULT: all 0 test file(s) passed`; the same empty-array guard already needed for the new selection logic was applied to the pre-existing file-list loop too. `tests/test-run-tests-for.sh` covers the `--for` mapping rules (including the always-run additions), the fail-safe full-suite fallback (both the explicit `tests/stubs/*` case and an unmapped path), `--changed` against both an uncommitted and a since-committed change on a fake base ref, an unresolvable `--changed` ref falling open to the full suite, and composition with `-j`. `agents/developer.md`, the README config table and Tests section, and `docs/user-guide.md` now describe the real flags. No version bump.
- **`pipeline-config.sh` warns on unknown `talos.pipeline.*` config keys instead of silently ignoring them (#176).** A typo such as `merge.atuo: false` or `limts.max_fix_attempts: 3` previously fell through the existing "missing key returns the caller's default" path with no signal at all -- the pipeline ran with defaults and the operator had no way to know their config wasn't doing anything. Both the `--dump` path (what `pipeline-cfg-cache.sh`'s `cfg()` answers every lookup from) and the single-key lookup path now compare every key actually present in the parsed config against an explicit 67-entry known-key list kept in `pipeline-config.sh` (both paths parse the file independently in separate `python3` processes, so the list and matcher are duplicated verbatim between them, same pattern as the existing `_validate_int_key` duplication). Wildcard segments (`agents.roles.*.model`, `agents.roles.*.runner`, `agents.roles.*.runner_cmd`, `board.statuses.*`, `board.status_map.*`, `board.azure_states.*`) match dynamic per-role/per-status keys without listing every possible role or status name; `_note` keys (used by `talos.pipeline.json.example` to document JSON's lack of comment syntax) are always ignored. An unknown key prints exactly one line to stderr -- `pipeline-config: [warn] unknown config key 'limts.max_fix_attempts' (did you mean 'limits.max_fix_attempts'?)` -- via `difflib.get_close_matches` against every known key with the query's own segment substituted for wildcard positions, so a typo under a dynamic key (e.g. `agents.roles.developer.modle`) still gets a precise suggestion (`agents.roles.developer.model`) instead of a bare wildcard template. Warns only: stdout and exit codes are byte-identical whether or not a typo is present, and an unknown key still falls back to the caller's default exactly as before. Set `TALOS_CONFIG_STRICT_KEYS=0` to silence the warning entirely. `tests/test-config-unknown-keys.sh` covers a top-level typo, a nested wildcard typo, a valid wildcard key producing no warning, both example configs producing zero warnings, `_note` being ignored, the warning firing exactly once per `--dump` invocation, stdout staying byte-identical with and without a typo, the env opt-out, and the single-key path warning independently of `--dump`. **QA follow-up:** the `--dump` path's warning never actually reached an operator through any real caller -- `pipeline-cfg-cache.sh`'s `cfg()` (sourced by `pipeline-vcs.sh`, `pipeline-notify.sh`, `pipeline-status.sh`, `pipeline-agent.sh`, and `pipeline-worktree.sh`) populated its cache with `pipeline-config.sh --dump ... 2>/dev/null`, silently discarding the warning for every one of those scripts; only a direct, non-cached `pipeline-config.sh --dump` invocation (as in the test suite above) ever showed it. The blanket stderr redirect had no documented purpose -- `--dump`'s "no config file found" path exits before touching python3 and writes nothing to stderr -- so it is simply removed; `tests/test-config-unknown-keys.sh` adds a case driving the warning through a real cache consumer (`pipeline-vcs.sh --dry-run`) end to end. No version bump.
- **Compact stage handoff: `view-issue --spec` and `diff-pr --stat` so agents stop re-ingesting whole issue threads (#201).** A busy issue thread accumulates a verdict/marker/attempt comment per stage, so by the time security runs, `view-issue` returns 10+ comments every stage re-ingests in full -- measured at 12,096 bytes for a single closed issue. New `pipeline-vcs.sh view-issue <n> --spec` (`github`/`github-api` parity) prints the same `{title, body, labels, comments}` shape, but `comments` is trimmed to at most the latest comment whose body starts with `**PM spec:**`: every `<!-- talos:` marker comment, every stage-verdict comment (body starting with `**Agent:**`), and every other comment (including a plain human reply -- the spec is the contract, not the thread) is dropped. It reuses the existing paginated `read-comments` verb, so no new fetch is added; measured reduction is 81% (12,096 -> 2,299 bytes) on the issue used for the original measurement. `gitlab`, `azure`, and `file` fall back to the plain full view with a stderr note. New `pipeline-vcs.sh diff-pr <pr> --stat` (`github`/`github-api` parity) prints a `git diff --stat`-style per-file additions/deletions summary derived from the same paginated PR-files endpoint `pr-files` (#200) already uses -- `--files` itself was already covered by `pr-files`, so this closes the remaining half of the original filing's item 2. `skills/pipeline/SKILL.md` and `agents/{developer,qa,reviewer,security,docs}.md` now call `view-issue <n> --spec` on the first issue read for developer and QA (adding the developer fix-round's read explicitly), with a sentence directing agents to the full thread (`view-issue` without `--spec`, or `read-comments`) only when a prior verdict is referenced (fix rounds); reviewer and security now read `diff-pr --stat` before the full diff. Developer (fix-round re-dispatch), QA, reviewer, and security prompt blocks in `skills/pipeline/SKILL.md` also gain a `Prior stage summary: <PRIOR_STAGE_SUMMARY>` placeholder the orchestrator substitutes with the last `pipeline-notify.sh` relay, so a re-dispatched or downstream stage does not have to find that context by reading the thread. `tests/test-view-issue-spec.sh` covers a fixture thread (PM spec, a validator verdict, an approval marker comment, an attempt marker comment, and a plain human comment) for both providers, plus `diff-pr --stat` against a stubbed paginated files endpoint; `tests/test-skill-names.sh` asserts every role prompt's first `view-issue` call uses `--spec`. No version bump.

- **Foreground rule placed directly beside every verify instruction, so developers stop backgrounding the suite and stalling (#205).** Rule 17 in `skills/pipeline/SKILL.md` already forbade background execution, but as prose ~400 lines from the actual verify instructions, developer subagents backgrounded `verify:` and ended their turn to "wait for the notification" three times (#166, #173, #196), each costing a stalled round trip the orchestrator had to notice and nudge. QA did the same with its bounded `pr-checks` poll under `qa_mode: ci` on PR #206. A one-line rule -- "run verify in the foreground with an explicit timeout of `<VERIFY_TIMEOUT_MS>` ms; never use background execution, `&`, `nohup`, `disown`, or sleep-polling; never end your turn while a verify command is running" -- now sits within 5 lines before both developer prompt variants' verify step and the QA prompt's verify/CI-wait decision in `skills/pipeline/SKILL.md`, and before the equivalent instructions in `agents/developer.md` and `agents/qa.md`. The QA CI-wait poll is additionally written out as a literal, single bounded foreground command (`until ... pr-checks ... ; do sleep 30; done` with a deadline derived from `verify.ci_wait_s`) so there is nothing left to improvise. New config key `verify.timeout_ms` (default `600000`, read in Step 0, must be a positive integer -- a non-integer or non-positive value is rejected by `pipeline-config.sh` with a one-line stderr warning and falls back to the default) is documented in the README config table, `docs/user-guide.md`, and both example configs. `skills/pipeline/SKILL.md` Step 3c also gains orchestrator guidance: if a developer returns without a PR and its final message says it is waiting on a background job, the orchestrator resends the task once with the foreground instruction, then records the attempt via `record-attempt` and treats it as Blocked if the resend also fails to produce a PR. `tests/test-skill-names.sh` adds a grep-based regression asserting the rule text appears within 5 lines before every verify instruction across both developer prompt profiles, the QA prompt, and `agents/developer.md`/`agents/qa.md` (RED on the unpatched prompts), plus assertions that the CI-wait loop is written out literally; `tests/test-config.sh` covers `verify.timeout_ms`'s default, explicit override, and rejection of non-integer/non-positive values. **PR review follow-up:** security flagged `verify.ci_wait_s` as the one sibling config value still unvalidated before reaching the literal, agent-executed shell test -- `pipeline-config.sh` now validates it exactly like `verify.timeout_ms` (positive integer, else a one-line stderr warning and a fallback to the default). The reviewer separately flagged that the literal CI-wait loop aggregated *every* check `pr-checks` reported instead of scoping to `merge.required_checks`, which could both false-PASS (a required check GitHub hadn't scheduled yet was invisible while every reported check read "pass") and false-FAIL/needlessly burn the wait budget (an unrelated non-required check stuck pending). - **A single HTTP 429 / secondary rate limit no longer kills a pipeline run -- every network call in every provider now retries with backoff (#173).** Previously only `_github_api`'s `_ga_req` detected HTTP 429 at all, and it logged the reset time and exited 1 immediately with no retry; `_github` (`gh` CLI), `_gitlab` (`glab`), and `_azure` (`az`) had no rate-limit handling whatsoever, so one transient 429 partway through a long backlog aborted the whole run. Fixed with a single shared retry helper, `_with_retry`, that every adapter's network calls now route through -- the only place retry/backoff logic lives. `_github`, `_gitlab`, and `_azure` each define a scoped shadow function (`gh()`/`glab()`/`az()` calling `_with_retry ... command <tool> "$@"`) at the top of their adapter function, so every existing call site (~33 for `gh`, ~10 for `glab`, ~8 for `az`, including ones inside `_run gh ...`, `$(gh ...)`, and pipelines) is covered with zero call-site edits; an explicit wrapper function would have required touching every site and was guaranteed to drift the next time one was added. `_github_api`'s `_ga_req`, `_ga_diff_req`, and `_ga_fetch_all_pages` each gained a `*_once` single-attempt helper (their existing status/body parsing, unforked) that `_with_retry` drives in a loop. Retried: HTTP 429; GitHub 403 responses whose body mentions a secondary rate limit or abuse detection (curl path); `gh`/`glab`/`az` CLI invocations whose stderr matches a rate-limit pattern (case-insensitive: "rate limit", "429", "secondary rate limit", "abuse detection", "too many requests"). Not retried, fails immediately with prior behaviour: 401, 404, 422, and anything else that doesn't match. Backoff honours a `Retry-After` header when the transport supplies one, otherwise exponential starting at 2s, doubling each attempt, capped at 60s; total attempts default to `limits.max_retries` (new config key, default `5`) plus the original try, i.e. up to 6 by default. Each retry logs one line to stderr naming the attempt number and wait duration. A retried attempt's stdout/stderr is fully captured and discarded, not partially emitted -- only the final attempt (success, exhaustion, or a non-retryable failure) reaches the real stdout/stderr. `--dry-run` never reaches `_with_retry`: every verb already returns before its first network call in dry-run mode. `TALOS_RETRY_SLEEP_SCALE` (default `1`) scales every sleep; tests set it to `0` for instant runs. - **`pipeline-vcs.sh`: anchored issue-number matching in `check-closing-keyword`, sibling lookup, and `find-pr` (all providers).**
  The closing-keyword regex now appends `(?!\d)` so `Closes #571` no longer falsely matches issue 57.
  The sibling lookup and both `find-pr` implementations (github and github-api providers) replaced
  substring `in` checks with anchored regex — branch names use `(?:^|/)issue-N(?:-|$)` and body
  text uses `#N(?!\d)` — so `fix/issue-571-x` is never treated as a sibling of issue 57, and
  `#71` in a body is not returned by `find-pr 7`.
  Includes 17 new regression tests in `test-closing-keyword.sh` covering the exact QA-failed case
  (`Closes #571` must not match issue 57) and the symmetric false-negative (`Closes #57` must still
  block when a sibling is open).

### Security

- **SHA-scoped approval gate closes the stale-label attack surface.** Prior to
  this change a force-push after an approval left the label in place; the merge
  gate checked only label presence, not which commit the label was earned against.
  `check-approval-sha` is fail-closed: an unresolvable head SHA, a missing marker,
  or a `git diff` failure all exit non-zero and block the merge.  Waiver config
  entries that are too broad (catch-all or covering non-waivable paths) are
  rejected at validation time using the same canary approach as `check-pr-files`.

- **`_is_lane_home` guard in `pipeline-worktree.sh`.** `remove <N>` and `sweep` now refuse to delete a worktree that contains a `.talos-lane-home` marker file. The file is placed by the operator in every long-lived lane home (never committed); it never propagates to disposable per-issue worktrees. Prevents a sweep run from one lane from deleting another lane's working directory.

- **`_is_self` guard in `pipeline-worktree.sh`.** `remove <N>` and `sweep` now refuse to delete the checkout they are running from. In inline harnesses (`agents.runner: pi`) the developer stage works directly in the orchestrator's own checkout, which can match the per-issue branch pattern; removing it would destroy the running session. In subagent mode the guard is a no-op.

- **Multi-lane sweep interlock.** When more than one `.talos-lane-home` marker exists among a repo's worktrees, `sweep` exits 0 without touching anything (safe no-op). Set `TALOS_SWEEP_ALL_LANES=1` to override. The per-issue `remove <N>` verb is always unaffected. Prevents cross-lane sweep collisions in repos that share one remote across multiple pipeline lanes.

- **Lane-scoped `list-prs`.** `pipeline-vcs.sh list-prs` now passes `--base "$BASE_BRANCH"` (from `base_branch` config) to `gh pr list` and includes `baseRefName` in the `--json` field list. Without lane scoping, Step 1 reconciliation in a multi-lane repo can adopt another lane's open PR and merge it into the wrong base. This happened: the qwen-lane sweep merged a canonical-lane PR (base `main`) into `qwen`.

- **`merge.forbidden_files_allow` config key.** An explicit allow-list checked **before** the deny patterns in `check-pr-files`. Glob-matched against filename and full path. Solves the case where a deny pattern (e.g. `.env.*`) over-matches a committed template (`.env.example`) that cannot simply be renamed. See README for usage.

- **Semantic canary validation in `merge.forbidden_files_allow`.** Allow-list entries are now validated by testing them against canary paths derived from the active deny patterns using the same `fnmatch` rule the gate uses (basename AND full path). An entry is rejected if it would exempt any canary. This replaces the previous character-stripping approach, which caught `*` and `**` but was bypassed by `*/*`, `**/*`, `*[!x]*`, `[a-z]*`, and `config/*`. The validator generates three canary forms per deny pattern (root, nested `sub/dir/<name>`, and prefixed `config/<name>`) so it catches both basename-level and path-level bypasses. The gate fails closed on any invalid entry, naming the entry and the canary it would have exempted.

### Removed

- **`.github/workflows/tests.yml`: removed `paths-ignore: ['**.md']` from the `pull_request` trigger (#160).** The clause evaluated the head commit rather than the PR's cumulative diff. A PR whose final commit touched only markdown produced no run at `ready_for_review` time -- code changes committed earlier as drafts were skipped by the job guard, and the `ready_for_review` event was then filtered by `paths-ignore`. The draft guard (`if: github.event.pull_request.draft != true`) is preserved and continues to skip runs while a PR is a draft. Markdown-only PRs now produce a run; the suite passes in under 30 seconds and the PR merges with a green signal rather than no signal. Cost: upper-bound 2-4 additional runs/day at under 30s each; the draft guard saving is fully preserved.

- **`scripts/pipeline-vcs.sh` `post-approval`: removed duplicate-marker detection (#156).** The check fetched comments via `gh pr view --json comments`, which caps at 100 and does not paginate. On a PR past that threshold the check ran, found nothing, and printed no warning -- silence that was indistinguishable from "no duplicate found". A warning that silently stops working past 100 comments is worse than no warning. The block is deleted; `post-approval` still exits 0, posts the marker, and applies the label unchanged. Re-stamping at the same SHA continues to work exactly as before (#136 required four re-stamp rounds without issue).

## [0.11.0] - 2026-08-11

### Fixed

- **`comment-issue` / `comment-pr` silently discarded the body when given `--body-file`.** The provider branches took `"$2"` as the body verbatim, so `comment-issue 42 --body-file verdict.md` ran `gh issue comment 42 --body "--body-file"` — a comment whose entire content was the literal flag, the real text dropped, **and exit 0**. Nothing failed and nothing warned. Three subagent verdicts were lost in a single pipeline run (two validators and one QA), and they were only caught because two later agents read the issue and found the verdicts missing.

  The trap is in the verb list itself: `comment-issue <n> <body>` sits four lines from `create-pr <branch> <title> <body-file>`. One takes inline text, its sibling takes a path — so an agent composing a multi-KB markdown verdict reaches for `--body-file` by analogy, with this script's own siblings and with `gh`. Treating that as agent error misses the point; the interface invited it.

  Wanting a file is legitimate rather than lazy, which is why the fix accepts it instead of only rejecting it: long markdown is hostile as a shell argument (backticks, `$`, quotes, newlines), and a body containing raw URLs can be refused outright by a permission rule, leaving a file as the only route.

- **`comment-issue <n> --body-file <path>` and `comment-pr <n> --body-file <path>`** now work, alongside an explicit `--body <text>` form. Normalisation happens before provider dispatch, so github, github-api, gitlab, azure and file mode all inherit it. The verb list documents both spellings.

- **A body that is still a bare flag is refused with exit 1** and a usage message naming both accepted forms, rather than being posted. An unreadable `--body-file` path also exits 1 and names the path. A body that merely *starts* with a single dash — a markdown bullet — is still a body, and is asserted as such.

It relocates the file and deletes the stale `.claude/talos/skills/pipeline/SKILL.md`, which is not merely tidiness — the AGENTS.md block written for the codex/antigravity harnesses pointed at that path, so a stale playbook there stays live for non-Claude runners after an upgrade. Only the file Talos wrote is removed; unrelated files you kept in that directory survive, and so do their parent dirs. Then **restart any Claude Code session already open in the repo** — skills are enumerated at startup.

- **The marketplace plugin is no longer load-bearing for `/pipeline`** — it remains useful for `/pipeline-setup` and for repos where `install.sh` has not run. #32's plugin-detection messaging is removed along with its `CLAUDE_CONFIG_DIR` probe: it existed to explain why a correct install had no command, and that premise is gone. The one surviving form of #31 — a session open *before* the install, holding a stale skill list, where `/pipeline` can still fuzzy-match an unrelated skill — is now the explicit closing note of the installer, along with the path the skill was registered at. README gains an Option A (installer), demotes the plugin to Option C, and states the discovery rule inline. (#34)

### Added
